# CPU Lab

Локальный испытательный стенд Intel CPU для Windows 11: автоматизация нагрузок,
синхронная телеметрия, история экспериментов и автономные HTML-отчёты.

## Порядок работы

- В начале сеанса читать [контекст продолжения](docs/continuation.md) и последнюю
  запись [журнала обсуждений](docs/discussions/README.md). История чата между
  компьютерами может быть недоступна; существенные знания не оставлять только в чате.
- После содержательного обсуждения обновлять контекст продолжения и добавлять
  датированную запись в журнал: решения пользователя, наблюдения, гипотезы,
  открытые вопросы и следующий шаг. Даты — Europe/Moscow; точное время не выдумывать.
  Не выдавать резюме за дословную стенограмму. Секреты и исходную персональную
  инвентаризацию в Git не помещать. Коммит и push выполнять при авторизации пользователя.
- Полное ТЗ: [docs/Codex_CPU_Lab_TZ.md](docs/Codex_CPU_Lab_TZ.md).
- До реализации исследовать существующие решения и записать результаты в
  `docs/research.md`: первоисточники, версии, интерфейсы, лицензии, ограничения
  и статус проверки. Непроверенные возможности помечать явно.
- После разведки предложить архитектуру и план; реализацию MVP начинать после
  согласования. План согласован пользователем 20.10.2026: C#/.NET 10 CLI,
  сначала mock-ядро, журнал, отчёт и тесты. Подготовительная разработка без стенда
  разрешена; реальные нагрузки требуют отдельного подтверждения.
- Минимизировать ручные клики и перезагрузки. Не создавать собственный движок
  нагрузки или телеметрии без исследования готовых решений.

## Безопасность и достоверность

- Аппаратные настройки по умолчанию доступны только для чтения. Без отдельного
  согласования не писать MSR/PCI, не менять напряжения, лимиты, CEP, BIOS,
  микрокод, драйверы и защитные параметры ОС. Не обходить блокировки.
- Не воспроизводить опасный сценарий F18 + микрокод 0x104 + BIOS offsets:
  ранее он привёл к no-POST. Автоматическую перепрошивку не предлагать.
- Реальные тяжёлые нагрузки запускать только после подтверждения оператором
  сценария и временных лимитов. На чужом стенде нужно разрешение владельца.
- CEP-induced clock stretching — гипотеза, а не установленная причина.
  Core Clock не равен Effective Clock, VID не равен физическому Vcore;
  peak power не заменяет среднюю мощность в окне теста.
- Различать измеренное, введённое пользователем, косвенно выведенное и неизвестное.
  Отсутствующие датчики обозначать `unknown/unavailable` с причиной, не нулём.
- Сохранять исходные данные, timestamps, единицы и идентификаторы сенсоров.
  Исторические ручные результаты не дополнять вымышленной телеметрией.

## Будущий MVP

- CLI, сменные TelemetryProvider и BenchmarkAdapter; Inventory, ScenarioRunner,
  RunStore, Analyzer, ReportGenerator и независимые HardwareProfile.
- Стенд A: i5-13600KF / Gigabyte B760 GAMING X DDR5 rev. 1.0 / BIOS F18.
  Стенд B: i7-14700KF / MSI Z790 Tomahawk; точная модификация и BIOS неизвестны.
- Уточнение пользователя 22.10.2026: по умолчанию достаточно одного прогона;
  повторять при неправдоподобном результате или для проверки конкретной гипотезы.
  Три повтора в исходном ТЗ и mock/probe fixtures — прежний план и тестовые сценарии,
  не обязательное требование пользователя. Частичные логи при сбое и отмене,
  CSV/JSON и автономный HTML. Никаких обязательных облачных зависимостей.
- Проверять парсеры на фикстурах и иметь mock-режим без тяжёлых нагрузок.
  Команды сборки и тестов документировать после выбора стека.
- Не коммитить реальные логи, персональную инвентаризацию, секреты,
  сторонние исполняемые файлы и прошивки. Лицензию проекта выбирать отдельно.

## Разработка

- Сборка: `dotnet build CpuLab.sln`; тесты: `dotnet test CpuLab.sln`.
- Безопасная демонстрация: `dotnet run --project src/CpuLab.Cli -- mock
  --scenario scenarios/mock-demo.json --legacy fixtures/legacy/manual-results.json`.
- Не выдавать фикстуры парсеров за stdout реальных Windows-прогонов.
- Mock-данные, часы и топология синтетические; везде сохранять эту маркировку.
- Обычные тесты и CI не должны запускать стресс-тесты, драйверы или MSR-команды.
- ProcessSupervisor проверять только на собственном лёгком ProcessProbe.
  Host должен оставаться за gate до назначения Job/группы; нельзя запускать
  целевую программу при ошибке containment. Windows-проверки не считать
  выполненными по одному факту сборки на Linux.
