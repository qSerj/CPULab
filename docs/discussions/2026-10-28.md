# 28.10.2026 — инструментарий Linux

Дата Europe/Moscow. Содержательное резюме, не дословная стенограмма.

Пользователь спросил, какие инструменты применять для нагрузок и мониторинга
под Linux, отметив, что смысл испытательного стенда существенно не меняется.
Переход проекта на Linux не объявлен согласованным решением.

По первоисточникам проверены stress-ng, Linux-версия y-cruncher, Linux CLI
7-Zip, turbostat, hwmon/coretemp, powercap/RAPL и OCCT Enterprise. Результаты
и ограничения записаны в разделе Linux в research.md. Предложение ассистента:
stress-ng + y-cruncher + фиксированный benchmark 7-Zip; turbostat с дополнением
hwmon/RAPL. OCCT Enterprise — готовая коммерческая альтернатива. Intel PCM
остаётся дополнительным исследовательским инструментом с ранее отмеченной
оговоркой о программировании PMU.

Принцип опыта прежний: фиксированный сценарий, синхронное окно телеметрии,
результат работы, средняя мощность/энергия, температуры и частоты. Для P/E-ядер
нужны отдельная идентификация и контроль размещения потоков. Между ОС отдельно
фиксировать ядро, микрокод, политику частот, версию и профиль теста; старый R23
не является baseline для другого Linux benchmark. Не обещать доступность
VR VOUT/Vcore/CEP и полное совпадение семантики часов с HWiNFO.

Установки, инвентаризация машины и нагрузки не выполнялись. Следующий шаг,
если Linux выбран: read-only проверка доступных источников на целевой системе,
затем согласование одного ограниченного сценария. Архитектура CPULab сохраняет
сменные TelemetryProvider/BenchmarkAdapter; реализация новых адаптеров не начата.

Пользователь отдельно заинтересовался скачками температуры под нагрузкой:
эта динамика сама по себе является предметом опыта. В 20 sysfs-чтениях guard
package держался 25 C до ~0.91 s после gate и стал 59 C на ~1.01 s; максимум
всех CPU-каналов вырос до47 C уже на ~0.40 s. **Уточнение ограничения:**
проверен исходник upstream Linux v6.12 drivers/hwmon/coretemp.c, show_temp:
MSR перечитывается после last_updated+HZ, то есть примерно раз в секунду.
Чтение каждые0.1 s не является свежим измерением каждые0.1 s; разные каналы
могут иметь разные моменты обновления кеша. Точную длительность фронта нагрева
и субсекундный максимум эта запись не устанавливает. Guard на sysfs также
ограничен кешем, даже если цикл проверки чаще. Никаких новых нагрузок нет.
Следующий опыт стоит планировать с отдельными baseline/нагревом/остыванием,
явными timestamps и проверенной частотой обновления выбранного источника;
для более частой температуры исследовать прямое чтение DTS готовым turbostat,
не обещая точность частот/мощности на столь коротких интервалах.

По исходным sysfs-чтениям построен temperature-pulse.png/svg; график показывает
ступени полученных кешированных значений, не реконструирует физическую кривую.
Включён в report.html как встроенное изображение, чтобы отчёт оставался автономным.

### Возврат к цели после замечания пользователя

Пользователь спросил, зачем отдельный опыт с нагревом/остыванием и какова цель.
Заинтересованность скачками температуры не была поручением исследовать тепловую
динамику. Ассистент признаёт уход в побочную тему. Основная ранее заданная цель —
больше производительности при заданном бюджете мощности (прежняя опора125 W),
с обоснованным выбором настроек. Linux-пара инструментов нужна для измерения
результата, средней мощности/энергии, частот и температур в одном окне.
Функциональная проверка пары завершена; отдельный тепловой опыт не нужен.
Следующий содержательный шаг — определить текущую опорную конфигурацию после
сброса настроек и рабочий бюджет мощности, затем выбрать репрезентативную задачу
для baseline и сравнения изменений.125 W не считать уже установленными; новые
BIOS-настройки и реальные нагрузки автоматически не назначены/не выполнены.

### Выбран критерий производительности и масштаб задачи

Пользователь уточнил привычную Windows-схему: Cinebench R23 несколько минут,
затем score. После объяснения согласился с критерием y-cruncher: меньше секунд
на одинаковую задачу означает выше производительность. Его новое пожелание —
одна задача, рассчитывающаяся примерно минуту. **Оставляем y-cruncher + turbostat**;
смена benchmark на другие программы не нужна. Stress VT3 не является следующим
согласованным шагом: он не отвечает выбранному критерию времени фиксированного
расчёта. Размер задачи подбирается один раз для исходной конфигурации, затем
сохраняется при сравнении настроек, а не подгоняется каждый раз под60 s.

Read-only проверка: доступно около2 GiB RAM при16 GiB общей памяти. Для большего
расчёта нужно обеспечить достаточную доступную RAM, чтобы не измерять подкачку.
Точный объём цифр/потребление памяти и предельный timeout ещё не назначены.
Чужие процессы не завершались, swap/защитные параметры не менялись, нового
расчёта не было. CLI Custom Compute позволяет задать произвольное число цифр,
если стандартные benchmark размеры окажутся неудобны; выполнение не проверялось.

### Текущий компьютер оставляем как есть; исходная проблема на другом стенде

Пользователь прямо решил прекратить дальнейшую настройку и тесты текущего
компьютера: существующая связка CPU/платы/кулера его устраивает, пусть работает
как есть. Затем объяснил исходную мотивацию: **другой процессор на другой плате**
достигает своей Tjmax и троттлится. Это сообщение оператора о другом стенде,
не результат проведённых здесь Linux-измерений; точная связка в этом уточнении
не названа. Не подставлять автоматически стенд A или B и не переносить на него
условия/результаты текущего12700F.

Прежняя формулировка «больше производительности при заданной мощности» описывала
один из этапов обсуждения текущего ПК, но не должна подменять исходную проблему
другого стенда. Для продолжения на проблемной машине цель — установить причину
достижения Tjmax/thermal throttling и выбрать обоснованное решение с оценкой
производительности. Не считать охлаждение, BIOS-лимиты или напряжение уже
установленной причиной. Никаких новых действий с текущим компьютером не нужно;
его baseline и проверенные Linux-инструменты сохранены для будущей работы.
