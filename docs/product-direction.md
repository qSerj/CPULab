# CPU Lab: цель продукта и проверка готовых альтернатив

21.10.2026. Зафиксировано по уточнению пользователя. Описание потребности и
предложение дальнейшей проверки; новый стек/GUI/план реализации не утверждены.
Согласованная архитектура 20.10 сохраняется как текущая основа, пока сравнение
альтернатив не даст оснований для изменения.

## Для чего нужен продукт

Пользователь ведёт несколько компьютеров с разными платами и хочет уменьшить
ручное переключение программ, чтение разрозненных логов и повторные входы в BIOS.
Нужен связный путь от смысла настройки до результата эксперимента:

`компьютер → плата/revision/BIOS → карта параметров → вариант настроек → серия → эффект → публикация`

Карточка компьютера включает CPU, плату/revision, BIOS, охлаждение, БП, память и
другие условия. Что можно определить достоверно — подхватывается автоматически;
неопределяемые компоненты вводятся один раз с отметкой источника. Изменение
комплектующих создаёт новую версию конфигурации; прежние эксперименты сохраняют
свой снимок.

Карта BIOS связывает исходное название/путь меню с техническим смыслом, единицами,
вариантами/диапазоном, условиями, применимостью к CPU/плате/прошивке, документом
или фрагментом анализа и степенью уверенности. Справочник строится по документации,
официальным образам и готовым экстракторам. Реверс нужен для определённого пробела
в семантике/обработчике, а не для повторения уже существующего parser.

Вариант настройки хранит изменения относительно предыдущего варианта. Программа
различает заявленный оператором ввод, прочитанное состояние после загрузки и
измеренный эффект. Отсутствие разницы в температуре само по себе не позволяет
объявить настройку неприменённой. Диагноз должен содержать наблюдения, гипотезы,
неизвестные и следующий проверяемый вопрос.

Нагрузки, диагностические программы и телеметрия подключаются через готовые
CLI/логи/shared memory/API. Пользователь работает с общей сессией; исходные файлы
остаются доступны как доказательства. Автоматическое изменение аппаратных
параметров и прошивок не входит в это уточнение.

Общий каталог нескольких ПК и обмен результатами предусмотрены в модели с самого
начала. Первая публикация может состоять из автономного отчёта и пакета данных;
сервер/облако — отдельный этап. Публичный пакет должен позволять выбрать состав
данных без обязательной передачи персональных идентификаторов.

## Что проверить раньше дальнейшего расширения реализации

1. **Готовая платформа.** Сопоставить OCCT Enterprise и PTS/Phoromatic с одним и
   тем же сценарием: несколько ПК, варианты условий, три повтора, синхронные
   показатели, сравнение, частичный результат, переносимый отчёт. Отдельно проверить
   нужные Windows-датчики и возможность внешней интеграции. Документация уже
   исследована; execution остаётся отдельной квалификацией.
2. **Готовый BIOS pipeline.** Аудировать `bios-tuning` и UEFIExtract/IFRExtractor,
   закрепить версии/hash, извлечь каталог из официального образа стенда A офлайн.
   Для выбранных настроек сохранить происхождение, диапазон, смысл, зависимости
   и неизвестные. Не прошивать и не писать Setup/MSR.
3. **Решение по переиспользованию.** Выбрать по результатам: расширять готовую
   платформу, интегрировать её как внешний инструмент или сохранить нынешнее ядро
   и реализовать недостающую связь. Основание — проверенные пробелы, стоимость
   интеграции и условия распространения, а не объём уже написанного кода.
4. **Один цельный путь.** Спроектировать карточку ПК, вариант настроек, запуск
   серии и сравнение двух вариантов на одном стенде. Зафиксировать критерии, по
   которым результат помогает пользователю решить следующий диагностический шаг.
5. **Обобщение и обмен.** Второй профиль без переписывания ядра, локальный каталог
   нескольких машин, затем публикация отчётов/каталогов с источниками знаний.

Реальные тяжёлые нагрузки требуют отдельного подтверждения сценария и лимитов.
Проверки готовых платформ сначала документальные/офлайн, затем лёгкие процессы
или заранее согласованный пакет на Windows. В обычный CI они не добавляются.

## Критерий полезности первой цельной версии

Из двух вариантов одного компьютера пользователь за один просмотр получает:

- что было изменено и какой смысл изменения подтверждён источниками;
- что удалось прочитать после загрузки и чего прочитать не удалось;
- какие тесты и версии использовались, завершилась ли серия, пригодны ли окна;
- как изменились производительность, мощность и температура в сопоставимых условиях;
- какие объяснения подкреплены данными, какие остаются гипотезами и чего не хватает;
- ссылку на воспроизводимые условия и исходные данные для обсуждения с другими.

Полного аналога по проверенной выборке пока не найдено. Это основание исследовать
стыки существующих решений, а не доказательство необходимости писать всё заново.
Матрица источников/версий/лицензий/статусов: [research.md](research.md).

## Практическая проверка на Windows

Пользователь 21.10.2026 выбрал **другой свой компьютер с Windows 11** для
первой инвентаризации/проверки датчиков без стресс-тестов. CPU/плата/BIOS этого
ПК пока неизвестны. Разрешения на реальные нагрузки, изменение BIOS, драйверов
или защитных параметров из этого выбора не следует.

Предлагается следующий порядок:

| Этап | Действия | Проверяемый результат |
|---|---|---|
| 1. Факты о ПК | Снять доступную inventory и версии утилит; охлаждение/БП указать вручную, если чтение недоступно. Текущие настройки сохранить как исходные | Карточка ПК с источниками и unknown; никаких вымышленных полей |
| 2. Каталог и запись | На существующих правах/драйверах проверить каналы HWiNFO и OCCT; последовательно записать 2–5 минут обычной работы без запуска нагрузки | Исходные файлы, каталог, единицы, timestamps/UTC offset, интервал опроса, пропуски. Проверка формата не доказывает качество под нагрузкой |
| 3. Автоматизация | Для нашего кода — Windows build/test и собственные лёгкие ProcessProbe, отмена/timeout/recovery. Для OCCT — выяснить контракт внешних скриптов, сначала с лёгким процессом | Проверенная остановка своих процессов и сохранение частичных данных; Windows Job Object не признаётся проверенным по Linux-сборке |
| 4. Первый настоящий тест | После отдельного согласования инструмента/режима, времени, температурной политики и потери telemetry — один ограниченный пилот в текущих настройках | Временные ряды с привязкой к старту/окончанию, доступные датчики, исходный результат и проверка остановки |
| 5. Повторяемая серия | После пилота — утверждённый пакет минимум из трёх последовательных попыток с паузами и общим пределом времени | Разброс внутри одного варианта и непрерывные данные, все индивидуальные результаты |
| 6. Вариант B и другие ПК | После устойчивого baseline согласовать конкретное изменение; повторить тот же пакет. Затем квалифицировать нужные каналы на стенде A | Сравнение двух вариантов; результаты чужой платы не переносятся на A как проверенные |

Предварительное чтение образов BIOS и документов выполняется параллельно без
перезагрузки компьютера. Для каждого источника сначала проверяется документированная
возможность, затем реальные каналы, затем сохранение/воспроизведение данных.

### Динамика — обязательный критерий выбора

- Сохраняются полные временные ряды до нагрузки, внутри неё, в паузах и после,
  с исходными timestamps, единицами, sensor IDs и интервалами усреднения.
- Видны температура, Package Power, Core Clock и Effective Clock отдельно,
  VID и доступный измеренный канал напряжения отдельно, доступные flags.
  Нет канала — указана причина; значение не дорисовывается.
- Два прогона можно сопоставить по времени относительно начала нагрузки,
  одинаковым единицам/шкалам и известным фазам. При неустановленном load window
  границы процесса помечены как иной источник; длительности не растягиваются
  незаметно, пропуски не заполняются для улучшения графика или статистики.
- Min/max и итоговый балл остаются дополнением к кривым. Можно проверить,
  когда возникло ограничение, как шёл прогрев и что изменилось во втором варианте.
- Временной ряд можно заново построить из сохранённого набора без датчиков,
  повторного теста и обязательного облачного сервиса.

Текущее ядро уже строит mock-графики. HWiNFO CSV importer сохраняет реальные
временные наблюдения, но его отчёт пока ограничен каталогом/min/max. Графики
и сравнение реальных импортированных рядов, live provider и реальные adapters
пока не реализованы. Это открытые работы, а не уже выполненные возможности.
