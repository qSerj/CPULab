# Первый доступ к Windows-ПК по локальной сети

22.10.2026. Пользователь разрешил SSH-доступ к своему Windows-ПК
в сети 192.168.143.0/24. Адрес и учётная запись получены; отпечаток сверен
с переданным connection.txt, вход по ключу проверен. Конкретные параметры
подключения и inventory остаются в игнорируемом runs/remote-access.
Сам факт SSH-доступа не разрешает реальные нагрузки. Отдельное последующее
разрешение ограниченного baseline описано в research.md.

Целевой путь: однократный bootstrap → проверенный SSH → автоматическая inventory
и передача файлов → квалификация датчиков → согласованный ограниченный пакет
нагрузок. Git и .NET SDK на стенде не нужны для самого SSH. Дальнейшие зависимости
переносятся по сети или с накопителя; их наличие пока не проверено.

## Пакет настройки

Сборка на машине разработчика (нужен Python 3, на Windows он не нужен):

```bash
python3 scripts/windows-ssh/package.py --public-key /path/to/client.pub --output runs/remote-access/CPUlab-SSH.zip
```

После подтверждённого отказа Windows Update 0x8024402C подготовлен также
`runs/remote-access/CPUlab-SSH-offline.zip` (~7 MB) с официальным MSI x64
Win32-OpenSSH 10.4.0.0p1-Preview. Вариант **Preview / non-production ready**
явно отмечен в инструкции и launcher; это не встроенный стабильный FoD.

```bash
python3 scripts/windows-ssh/package.py --public-key /path/to/client.pub --offline-msi tools/openssh/10.4.0.0p1-Preview/OpenSSH-Win64-v10.4.0.0.msi --output runs/remote-access/CPUlab-SSH-offline.zip
```

MSI скачивается с официального релиза, его закреплённый SHA-256 проверяется при
упаковке и перед установкой. На Windows дополнительно проверяется Authenticode
Microsoft. Уже зарегистрированная служба используется без повторной установки;
путь ssh-keygen берётся из расположения фактического sshd. Офлайн-установка MSI
не обращается к Add-WindowsCapability; ошибки пишутся в setup-error.txt, лог MSI —
openssh-install.log. Проверка сертификата может зависеть от доверенных корней/
доступности проверки цепочки; при невозможности верификации установка останавливается.

В ZIP попадают только launcher, его читаемый PowerShell-исходник, открытый ключ
и инструкция (в офлайн-варианте также MSI и его provenance). Закрытого ключа и inventory в нём нет. Результат под runs/ не
коммитится. Нужен обычный распакованный каталог, запуск прямо из ZIP не подходит.

На стенде: распаковать → SETUP-SSH.cmd правой кнопкой от имени администратора
нужной локальной/доменной учётной записи → передать connection.txt в чат.
Подробности изменений и ограничений: [README.txt](../scripts/windows-ssh/README.txt).

Launcher содержит прямую PowerShell-команду, без изменения execution policy,
EncodedCommand или загрузки кода из интернета. Если политики организации блокируют
такой запуск, обход не предусмотрен. Исполняется именно содержимое launcher;
после изменения Setup.ps1 пакет нужно пересобрать.

## Проверка подключения

После получения connection.txt сверить отпечаток host key по независимому
переданному файлу; не отключать StrictHostKeyChecking. Подключаться только к
сообщённому IP/учётной записи, не сканировать подсеть в поисках стенда.
При подключении из песочницы может потребоваться сетевое разрешение среды.
Пароль в чат не передавать. На нестандартном sshd_config проверить применимость
administrators_authorized_keys и существующих firewall rules.

Первая удалённая сессия — только чтение версии ОС/службы и inventory. Новые
изменения окружения и нагрузки выполняются в пределах явно согласованного этапа.

## Статус проверки

На Linux сформирован ZIP и проверены состав, целостность, длина CMD-команды,
CRLF и отсутствие закрытого ключа в скриптах; у офлайн-пакета дополнительно
сверен SHA-256 MSI с опубликованным upstream. Оператор подтвердил выполнение
первого launcher до сбоя Add-WindowsCapability 0x8024402C. Установка MSI/ACL/firewall,
реальная авторизация и достижимость стенда ещё не проверены. Linux-проверка
упаковки не подтверждает работоспособность Windows bootstrap.

Обновление после подключения: оператор подтвердил установку офлайн bootstrap;
SSH-аутентификация по ключу фактически проверена. SFTP работает при явном указании
сервера `C:/Program Files/OpenSSH/sftp-server.exe` и абсолютных путях `/C:/...`;
стандартный subsystem-вызов в этом окружении закрывал соединение. Конфигурация
sshd и защитные настройки при диагностике не менялись. Неудачные собственные
приёмщики stdin завершены адресно. Оператор самостоятельно установил SDK
10.0.401; 87/87 тестов и CLI-серия исполнены на Windows, см. validation.md.
